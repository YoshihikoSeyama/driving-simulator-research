# レンタカー「物知りおじさん」アプリ構想

- 調べた日付: 2026-08-14
- 目的: 「レンタカー予約サイトからは分からないが実際には気になること」を教えてくれるアプリの実現可能性を検討する
- 情報源: 本ファイルは構想・設計の整理。事実確認は同ディレクトリの調査メモ（CarPlay / 保険 / データ源 / 実例）を参照

---

## 1. 何が課題なのか（問題の再定義）

ユーザーの原案:

> CarPlay が使えるかは車種・開発年代によるが、レンタカーサイトからは分からない。
> 保険もよく分からないまま最上級に入っている。それって本当に必要か。
> 実際に借りてがっかりする点、知っていれば得な情報を吐いてくれるアプリが欲しい。

これを構造化すると、課題は3層に分かれる。層ごとに難易度と必要な技術が全く違う。

| 層 | 課題 | 本質 | 難易度 |
| --- | --- | --- | --- |
| L1 | **借りる車が確定しない** | レンタカーは「車種クラス指定」が原則。予約時点で車両が決まらない | 構造的・最難関 |
| L2 | **車両の装備が分からない** | 車種・年式・グレード・オプションで装備が変わる。サイトは装備を開示しない | データ収集の問題 |
| L3 | **判断ができない** | 情報があっても、保険が必要かなど「で、どうすればいい？」が分からない | 推論・UXの問題 |

**重要な洞察**: L3（おしゃべりおじさん）だけを LLM で作るのは簡単だが、それは「一般論を喋るだけのアプリ」になり価値が出ない。既に ChatGPT に聞けば済む。差別化は L1・L2 の泥臭いデータ整備にある。

### L1 が最大の壁である理由

「トヨタ ヤリス または同等クラス」という予約に対して、当日出てくるのは
ヤリスかもしれないしフィットかもしれない。年式も分からない。
つまり **確定的な答えは原理的に返せない**。

これは技術で解ける問題ではないので、プロダクト設計で回避する必要がある。
→ 後述の「確率で答える」アプローチ。

## 2. 私の意見（率直に）

### 良いと思う点

1. **痛みが本物である**。旅行中の限られた時間で「CarPlay 使えない」「思ったより狭い」は
   取り返しがつかない。事前に分かれば行動が変わる（＝価値がある情報）。
2. **情報の非対称性がはっきりある**。貸す側は知っているが借りる側は知らない。
   この構造がある領域はサービスが成立しやすい。
3. **保険は金額インパクトが大きい**。1日1,000〜2,000円規模の意思決定を毎回、
   根拠なく行っている人が大量にいる。ここは説明価値が高い。
4. **LLM の得意領域と噛み合う**。断片的な口コミ・PDF諸元表・規約という
   「非構造テキストを読んで統合する」作業は従来コストが高すぎて誰もやらなかった。

### 懐疑的に見るべき点（ここを直視しないと失敗する）

1. **「確定情報を返せない」問題**。L1 のとおり。
   「たぶん CarPlay 使えます」で価値が出るのか、を最初に検証すべき。
2. **保険の助言は法的にグレーになり得る**。「この保険は不要です」と断定すると
   保険業法・景表法の観点でリスクがある（調査中）。
   → 「判断材料の提示」に徹する設計にすべき。断定は避け、損失額と確率を示す。
3. **データの鮮度が死にやすい**。料金・補償内容・車種構成は毎年変わる。
   一度作って放置すると即座に嘘をつくアプリになる。更新の自動化が必須。
4. **収益化が難しい**。予約はレンタカー会社側で完結するので、
   アフィリエイト以外の収益点が薄い。B2C 課金は「年数回しか使わない」ため厳しい。
   → むしろ B2B（レンタカー会社に「装備情報を出すと予約率が上がる」と売る）や
     メディア型（SEO + アフィリエイト）が現実的かもしれない。
5. **スクレイピング依存はスケールしない**。規約リスクと保守コストが乗る。

### 結論としての立場

**やる価値はある。ただし「全部答えるアプリ」を目指すと必ず失敗する。**

最初に作るべきは、対象を極端に絞った1機能。具体的には:

> **「この予約クラスで CarPlay が使える確率は何%か、そして当日ハズレを引いたときの回避策」**

これ1点で検証する。理由:
- CarPlay は Yes/No が明確で検証しやすい（＝仮説検証に向く）
- Apple 公式に対応車種リストがあるので、データの起点が存在する
- 「ハズレたときの回避策」（例: FM トランスミッター持参、Bluetooth で代替）を
  返せると、確率が曖昧でもユーザーに価値が出る ← ここが重要

## 3. プロダクトの形（3つの選択肢）

### 案A: 予約前チェックリスト型
予約情報（会社・クラス・地域・日程）を入力 → 気になる点を一覧提示。

- 長所: 実装が軽い。L1 の不確実性を「チェックリスト」として自然に扱える
- 短所: 情報アプリ止まりで再訪動機が弱い

### 案B: 対話型「物知りおじさん」（原案に忠実）
チャットで「沖縄で3泊、スーツケース2個、iPhone使いたい」→ おじさんが喋る。

- 長所: 原案の魅力そのまま。曖昧な質問に強い
- 短所: **裏側のデータがないと一般論しか喋らない**。ここが最大の罠
- 対策: RAG の根拠として L2 データを必ず引く。根拠が無い話はしない設計にする

### 案C: 予約直前の「差分アラート」型
予約確定後、当日までに「あなたの予約で注意すべき3点」を通知。

- 長所: タイミングが最適（行動を変えられる瞬間に届く）
- 短所: 予約情報の連携が必要でハードルが高い

**推奨**: **案A で作り、案B の顔をかぶせる**。
中身はチェックリスト（＝根拠のあるデータ）、UI は会話。
案C は後から足す。

## 4. 「確率で答える」アプローチ（L1 への回答）

確定情報が返せないなら、確率と対策を返す。

```
入力: トヨタレンタカー / コンパクトクラス(P1) / 那覇空港店 / 2026-09
       ↓
① クラス→車種候補の推定
   「P1クラス = ヤリス / パッソ / アクア のいずれか」（公式サイトの代表車種記載＋口コミ）
② 車種→年式分布の推定
   レンタカーは概ね1〜3年で入替 → 2023〜2026年式が中心
③ 車種×年式→装備の判定
   ヤリス2023-: ディスプレイオーディオ標準 → CarPlay 有線◯ 無線△
   パッソ: 2023年に生産終了、ナビはディーラーOP → CarPlay ✕ の可能性
       ↓
出力:
   CarPlay 使える確率: 約70%（根拠: 候補3車種のうち2車種が対応、うちアクアは無線対応）
   ハズレたときの対策:
     - Bluetooth 接続は全車ほぼ可能 → 音楽と通話は問題なし
     - ナビは車載を使うか、スマホホルダーを持参（100円ショップでも可）
     - 電話予約で「ディスプレイオーディオ付き車両希望」と伝えると通ることがある ←重要
   確実にしたい場合:
     - 車種確定できる会社/プランを使う（該当があれば提示）
```

**「確実にしたい場合」と「ハズレ対策」があると、確率が曖昧でも実用になる。**
これが本プロダクトの核心アイデア。

## 5. アーキテクチャ案

### 全体構成

```
┌─────────────────────────────────────────────────┐
│  UI（Web/LINE）  会話 or チェックリスト           │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│  回答生成レイヤ（LLM + RAG）                      │
│   ・根拠なし発言を禁止（引用必須）                 │
│   ・確率と対策をセットで返す                      │
│   ・保険は「判断材料」のみ提示、断定しない          │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│  ナレッジベース（ここが本体）                     │
│   ① クラス→車種マッピング表                       │
│   ② 車種×年式×グレード→装備表                    │
│   ③ 補償プラン比較表（会社別・料金・NOC有無）      │
│   ④ 落とし穴ナレッジ（口コミ由来、Q&A形式）        │
│   ⑤ 地域ナレッジ（沖縄/北海道/離島）              │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│  収集エージェント群（定期実行）                    │
│   各社サイト / メーカー諸元表 / Apple対応表 /      │
│   口コミ / 規約ページ                             │
│   → 差分検知 → 人間レビュー → KB更新              │
└─────────────────────────────────────────────────┘
```

### なぜマルチエージェントが効くのか

この課題は「情報源ごとに読み方が全く違う」のが特徴。
1つのエージェントに全部やらせると精度が出ない。役割分担が自然に生まれる。

| エージェント | 担当 | 出力 |
| --- | --- | --- |
| 装備調査 | メーカー諸元表PDF・Apple対応表 | 車種×年式×装備テーブル |
| クラス調査 | 各社サイトのクラス定義 | クラス→車種候補 |
| 補償調査 | 各社の規約・料金ページ | プラン比較表（金額付き） |
| 口コミ収集 | ブログ・レビュー・SNS | 落とし穴ナレッジ候補 |
| **検証** | 上記の出力を突き合わせる | 矛盾検出・信頼度スコア |
| 鮮度監視 | 前回との差分 | 更新アラート |

**検証エージェントが最重要**。口コミは間違いが多く、規約は改定される。
「複数ソースで一致したら信頼度高、1ソースのみなら要注意フラグ」という
多数決を機械的に回す。LLM の幻覚対策としても効く。

## 6. 段階的な作り方（実装計画）

### Phase 0: 仮説検証（コード書かない・1週間）
- CarPlay 1点に絞り、手作業で1社1クラス分のデータを作る
- 知人5人に見せて「これで予約前に見たいか」を聞く
- **ここで刺さらなければ作らない**

### Phase 1: 単一ドメインの縦切り（2〜3週間）
- 対象: トヨタレンタカー × CarPlay のみ
- ナレッジは手作りYAML/JSONで十分（DB不要）
- 出力は「確率＋対策」形式。UIは最小
- 収集の自動化はまだやらない

### Phase 2: ナレッジ拡張（1〜2ヶ月）
- 装備を CarPlay 以外に拡張（ETC・荷室・寒冷地仕様・燃料種別）
- 会社を3〜4社に拡張
- 収集エージェントを導入。**人間レビューを必ず挟む**（全自動にしない）

### Phase 3: 対話化・補償診断（1〜2ヶ月）
- 「物知りおじさん」の会話UIをかぶせる
- 補償診断を追加。ただし「あなたの条件での最大損失額はX円、
  カード付帯で重複している可能性がある項目はこれ」という**材料提示型**
- 断定表現は出さない（法務リスク回避）

### Phase 4: 鮮度維持の仕組み化
- 差分検知 → 通知 → レビュー のループを定常運用に
- ここを作れないと 1 年で嘘つきアプリになる

## 7. 技術スタック案

| 領域 | 選択 | 理由 |
| --- | --- | --- |
| ナレッジ | 最初はYAML/JSONをgit管理 | 差分がレビューできる。DBは早すぎる |
| 収集 | Playwright + LLM抽出 | JSレンダリング必須のサイトが多い。抽出はLLMに任せる |
| RAG | 構造化データ優先＋テキスト補助 | 装備表は構造化で持つべき。ベクトル検索だけに頼ると数値がぶれる |
| LLM | Claude（Agent SDK） | PDF諸元表の読解と長文規約の要約に強い。マルチエージェント構成が組みやすい |
| UI | LINE bot を第一候補 | 旅行前にスマホで見る文脈に最も近い。アプリDLの壁がない |

**設計上の原則（重要）**:
- 装備の Yes/No は **構造化データで持つ**。LLM に毎回推論させない（幻覚と非再現性の温床）
- LLM の役割は「収集時の抽出」と「回答時の説明」に限定する
- 全ての回答に出典を持たせる。出典が無い情報は返さない
