# 車版ChatGPT ―「能動的に教えてくれるAI」の構想

- 調べた日付: 2026-08-14
- 目的: 「ユーザーが質問を思いつかなくても、必要な情報を先回りして届けるAI」の設計を詰める
- 位置づけ: レンタカーアプリ構想（`2026-08-14-レンタカー物知りおじさん-構想.md`）の上位概念。
  レンタカーはこの構想の1ユースケースに格下げされる

---

## 1. ユーザーによる定義

> ChatGPT は自分で聞かないと答えてくれない。
> つまり**ペインポイントに自分で気づけていない場合、その回答に辿り着けない**。
> 車版ChatGPT は積極的に意見を出す。ChatGPTは受動、車版ChatGPTは能動。

この定義は正確で、しかも**製品の作り方を根本から変える**。以下でその含意を展開する。

---

## 2. 最重要の再定義: これは「回答生成」ではなく「質問生成」の製品である

### 2-1. 何が本当に不足しているのか

ユーザーの指摘を厳密に読むと、不足しているのは**答え**ではない。

- 「レンタカーでCarPlayは使えますか？」と聞けば、ChatGPTは十分な答えを出せる
- 問題は**その質問を思いつかないこと**

つまり:

```
ChatGPT   : 質問 →（LLM）→ 答え
車版      : 状況 →（???）→ 質問 →（LLM）→ 答え
                      ↑
                 ここが製品の本体
```

> **答えの生成は既にコモディティ。希少なのは「この人が今、何を知らないか」を特定する能力。**

この一文が本構想のすべて。これを外すと「車に詳しいチャットボット」になり、
ChatGPTとの差が消える。

### 2-2. 帰結: 作るべきデータ資産が変わる

「車のスペックDB」を作る発想になりがちだが、それは答え側の資産で、差別化にならない。

**作るべきは「後悔のカタログ」**:

```
状況（コンテキスト） → 「知らなくて損した/後悔した」事実 → 伝えるべきタイミング
```

前回のレンタカー調査で作った48件のQ&Aリストは、まさにこれの最初の断片。
あれは「アプリが答えるべき質問」として作ったが、実体は**後悔のカタログ**だった。
あれを車ドメイン全体に拡張したものが、この製品の中核資産になる。

### 2-3. 後悔は収集できる

質問は集めにくいが（思いついていないので存在しない）、**後悔は事後に集められる**。

- 「借りてみてがっかりしたことは？」
- 「買う前に知りたかったことは？」
- 「車検で想定外だったことは？」

**後悔は能動的助言のグラウンドトゥルース。** ここが収集設計の要点。

---

## 3. 能動性の設計 ― 最大の難所

### 3-1. 能動型アシスタントはほぼ全部死んでいる

Google Now、Cortana、Siri Suggestions ―「先回りして教えてくれる」系は
軒並み縮小・終了している（※詳細は調査中）。

一方で**定着している能動通知**もある:
- カレンダーのリマインド
- 天気の警報
- クレジットカードの不正検知
- 航空会社の遅延通知

**この差が何なのかを正確に理解することが、本製品の生死を分ける。**

現時点の仮説（要検証）:

| 定着した能動通知 | 死んだ能動通知 |
| --- | --- |
| **行動を変えられる**（まだ間に合う） | 情報として面白いだけ |
| **外れが少ない**（誤報率が低い） | 「たぶん興味あるでしょ」の推測 |
| **不作為のコストが明確**（放置すると損する） | 知らなくても特に困らない |
| ユーザーが**その通知を頼んだ自覚がある** | 勝手に始まった |
| **頻度が低い** | 毎日来る |

### 3-2. 「割り込み予算」という概念を持つべき

能動通知は**信頼を消費する**。これを明示的にモデル化する。

```
通知を発火する条件:
  期待価値（円 or 回避できる損害） > 割り込みコスト（信頼の消費）

かつ:
  一定期間内の通知回数に上限を設ける（＝予算）
  予算内で期待価値の高い順に選ぶ
```

車ドメインの強みは、**期待価値を円で計算できる**こと。

- 「この時期に売れば残価が◯万円高い」
- 「この特約は年◯円で、あなたの条件では使う可能性が低い」
- 「時間外返却で1日分（◯円）余分に取られる」

**円で言えない通知は出さない**、を初期ルールにするのが安全。

### 3-3. 具体性テスト

汎用的な通知は必ずうざくなる。判定基準を1つ置く:

> **「このメッセージは、他の90%のユーザーにとっては間違い or 無関係か？」**
> YESなら送ってよい。NOなら送らない。

「タイヤの空気圧は月1回チェックしましょう」→ 全員に当てはまる → **送らない**
「あなたの車の型式でリコールが出ています。未改修です」→ 極めて限定的 → **送る**

## 4. トリガーの分類 ― 「いつ喋るか」

能動性の実装は結局「トリガー設計」に還元される。

| 種類 | 例 | 強さ | データ取得 |
| --- | --- | --- | --- |
| **A. 公的記録トリガー** | リコール届出、法改正、補助金の期限 | ★★★ | 公開データ（要調査） |
| **B. カレンダートリガー** | 車検満了、保険更新、税の納期、13年超の重課、免許更新 | ★★★ | ユーザー登録＋制度知識 |
| **C. 状態トリガー** | 走行距離が閾値到達、タイヤ製造から◯年、バッテリー寿命 | ★★ | ユーザー入力 or 車両連携 |
| **D. 意思決定トリガー** | 予約中・比較中・見積もり取得中・契約直前 | ★★★ | アプリ内の行動 |
| **E. 環境トリガー** | 大雪予報、チェーン規制、燃料価格の変動 | ★★ | 気象・道路情報 |
| **F. 市況トリガー** | モデルチェンジ発表、中古相場の変化、売り時 | ★★ | 相場データ（要調査） |
| **G. 定期トリガー** | 「今月のお知らせ」 | ☆ | — |

**G（定期）は最弱で、これに頼ると必ず失敗する。** メルマガと同じになる。

### 4-1. 最も強いのは A と B

理由:
1. **ユーザーが原理的に気づけない**（リコールは通知が届かないことがある、
   制度の境界は知らない）→ 能動性の価値が最大
2. **公的データで検証できる**→ 誤報が出ない、出典を示せる
3. **不作為のコストが明確**→ 「知らないと損する」が言い切れる
4. **タイミングが自明**→ 期限から逆算するだけ

特に**リコール未改修**は理想的な題材（要検証）:
- 国交省が公開している
- 所有者に通知が届かないケースがある（転居・中古で所有者変更）
- 安全に直結する
- 「あなたの車が対象です」は極めて具体的
- ChatGPTには絶対にできない（ユーザーの車を知らないため）

### 4-2. D（意思決定トリガー）は価値が高いが取得が難しい

「契約直前」に「その保証は不要かもしれません」と言えれば価値は最大。
しかし**そのタイミングをどう検知するか**が難問。

現実解の候補:
- ユーザーが自分で「今、見積もり取ってます」と入れる（能動性が半減する）
- 予約確認メールの連携（Gmail連携等。プライバシーのハードルが高い）
- アプリ内で比較・検討させる（＝自社に行動を囲い込む）

## 5. コンテキストの獲得 ― 能動性の燃料

### 5-1. 能動性は「ユーザーが入力していない情報」を必要とする

ChatGPTが受動なのは、部分的には**ユーザーが話したことしか知らないから**。
能動化するには、聞かずに状態を持つ必要がある。

車ドメインで持つべき最小のコンテキスト:

```
車両:   メーカー / 車種 / 年式 / 型式 / グレード / 走行距離 / 車検満了日
契約:   任意保険（会社・等級・特約）/ ローン残債 / 駐車場
利用:   年間走行距離 / 主な用途 / 家族構成 / 雪国か
本人:   免許取得年 / 年齢 / 運転頻度
```

### 5-2. 登録のハードルをどう下げるか

これを最初に全部入力させると、ユーザーは離脱する。

**設計方針: 「車検証の写真1枚」から始める。**

車検証には 車種・型式・年式・車台番号・車検満了日・所有者 が載っている。
写真1枚（またはQRコード読み取り）で、A・Bトリガーの大半が発火可能になる。

> **オンボーディングの目標は「車検証を撮ってもらうこと」ただ1点。**
> ここを突破できれば能動性が起動し、できなければ何も起きない。

追加情報は**能動通知を出しながら少しずつ聞く**（「保険会社を教えてもらえれば
更新時期に見直し案を出せます」）。価値を先に見せてから聞く順番が重要。

## 6. 差別化の持続性 ― 直視すべき懸念

### 6-1. 「能動性」自体は汎用LLMに取り込まれつつある

これは正直に指摘しておきたい懸念。

ChatGPT / Claude 等は既に**メモリ**（ユーザーの情報を覚える）、
**スケジュールタスク**（定期実行）、**コネクタ**（外部サービス連携）を実装しつつある。
つまり「受動 vs 能動」という差は、**時間とともに縮まる可能性が高い**（※調査中）。

「ChatGPTは受動だから」を唯一の差別化にすると、機能追加1回で消える。

### 6-2. では何が残るのか

汎用LLMが能動化しても残るものは3つだと考える。

1. **後悔のカタログ**（何を伝えるべきかの知識）
   汎用LLMは「一般に知られていること」は言えるが、
   「実際に借りた100人のうち何人がこれでがっかりしたか」は持っていない。
   **自前で集めた後悔データは複製されない。**

2. **ユーザーの車の具体的な状態**
   型式・年式・走行距離・車検満了日・保険の等級。
   これを持っている側が能動通知を出せる。
   （ただしコネクタで取られる可能性はある）

3. **トリガーの網羅性と運用**
   リコールを毎日監視し、制度改正を追い、相場を見る。
   これは**継続運用のコスト**であり、汎用LLMは代行しない。

> **結論: 差別化を「能動性」に置くのではなく、
> 「能動性を成立させるための固有データと運用」に置くべき。**
> 能動性は結果であって、防壁ではない。

### 6-3. 逆に、汎用LLMの上に作るという選択肢

対抗せず乗る道もある。
「ChatGPT/Claude のコネクタ・MCPサーバとして車の状態とトリガーを提供する」形。
UIを作らず、データとトリガーだけを持つ。
検討に値する（収益モデルは別途要検討）。

## 7. プロダクトの形

### 7-1. 会話UIは「主」ではなく「従」

原案の「おしゃべりおじさん」は魅力的だが、
**能動型製品の主役はチャット画面ではなく通知**。

```
通知（能動）      ← 主。ここに価値がある
  ↓ タップ
説明カード         ← 根拠・金額・出典・次の行動
  ↓ 深掘りしたい時だけ
会話（受動）      ← 従。ChatGPT的な部分
```

チャットを主にすると「開かないと何も起きない」＝受動に逆戻りする。

### 7-2. 通知の型

すべての能動通知を同じ型に揃えると、品質が管理しやすくなる。

```
【何が起きているか】   あなたの車（◯◯・2019年式）に未改修のリコールがあります
【なぜ今か】           届出は2024年3月。まだ改修記録が確認できません
【いくらの話か】       改修は無償。放置すると◯◯のリスク
【何をすればいいか】   最寄りのディーラーに車台番号を伝えて予約（ボタン）
【出典】               国土交通省リコール情報（リンク）
【この通知が不要なら】 この種類の通知を止める（ボタン）
```

**「出典」と「止める」を必ず入れる。** 信頼と割り込み予算の管理装置。

## 8. 段階的な作り方

### Phase 0: 後悔カタログの手作り（コードなし）
- 車のライフサイクル全体で「知らなくて損した」実例を100件集める
- 各件に「トリガー」「金額インパクト」「自分で質問を思いつけるか」を付与
- **「自分で質問を思いつけない × 金額インパクト大」の象限だけを残す**
- ここが薄ければ製品は成立しない。最初に確かめるべき

### Phase 1: 単一トリガーの縦切り
- **リコール未改修の通知に絞る**（最も強いトリガー、要検証）
- 入力は車検証の写真1枚のみ
- 出力は通知1本と説明カード
- 「車版ChatGPT」の会話機能は**まだ作らない**

### Phase 2: カレンダートリガーの追加
- 車検満了、保険更新、13年超の重課、税の納期
- 車検証だけで大半が発火できるはず

### Phase 3: 後悔カタログの投入と会話化
- Phase 0 のカタログを状況に紐付けて配信
- ここで初めて会話UIをかぶせる

### Phase 4: 収集ループ
- 通知後に「役に立ったか」を聞き、割り込み予算のパラメータを調整
- イベント後（車検後・購入後・返却後）に後悔を収集し、カタログを育てる

## 9. 検証すべき仮説（調査に投げた項目）

- [ ] リコール情報は機械可読に取得できるか。型式/車台番号で判定できるか
- [ ] 未改修リコールがどれくらい残っているか（＝能動通知の価値の裏付け）
- [ ] 車検・税・保険など時間トリガーになる制度の境界の実態
- [ ] 中古相場・燃料価格の公開データの有無
- [ ] 能動型アシスタント（Google Now等）が失敗した理由の分析
- [ ] 定着した能動通知と失敗したものの差の定量的知見
- [ ] 通知疲れの研究知見（誤報率の閾値など）
- [ ] 汎用LLMの能動化（メモリ・スケジュール・コネクタ）の実装状況
- [ ] 車のライフサイクル全体での「知らなくて損した」実例
- [ ] 垂直特化AIアシスタントの実例と収益モデル

→ 結果を受けて本メモを改訂する。

## 10. 現時点での率直な評価

**強い点**
- 「受動 vs 能動」の定義が的確。ここを突いた製品は確かに存在しない
- 車は**金額インパクトが大きく、知識の非対称性が激しく、
  ユーザーの関与頻度が低い**（＝忘れる、気づかない）。能動型と相性が良い
- トリガーになる公的データが存在しそう（リコール・車検・税）

**弱い点／リスク**
- **能動型アシスタントの死屍累々**という歴史的事実。設計を誤ると必ず同じ道
- **能動性は汎用LLMに追いつかれる**。差別化を能動性そのものに置いてはいけない
- **コンテキスト獲得のハードル**。車検証を撮ってもらえるかが全て
- 車の保有者は「年に数回しか能動的に関わらない」＝アプリを開かない。
  だからこそ通知が主役だが、通知権限を切られたら終わる

**現時点の結論**
やる価値はある。ただし
**「車に詳しい能動的なチャットボット」を作ると失敗する。**
**「ユーザーの車の状態を持ち、公的データを監視し、
期限が来る前に円で語りかける仕組み」を作るべき。**
会話はその最後に足す薄い皮でよい。
